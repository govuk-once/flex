# Zap workflow

The ZAP workflow located in `.github/workflows` runs the OWASP ZAP tool (API scan) against the staging environment to identify vulnerabilities.


---

## Overview

The scan runs every time a deployment to staging is successful. The results are stored as an artifact of the run and can be viewed locally. To download the artifact, go to the Summary tab and scroll to the bottom of a successful ZAP run.

In addition to the downloadable workflow artifact, ZAP findings are uploaded in SARIF format to GitHub Code Scanning and can be viewed under `Security -> Code scanning`.

The workflow now generates the current OpenAPI definitions from the application code and creates a temporary merged OpenAPI document containing public API operations for the ZAP scan. This avoids relying on a static OpenAPI document which may become outdated.

The scan is authenticated using the JWT generated by `scripts/dastSetup.ts`.

## Scan results

ZAP produces HTML, JSON, Markdown and SARIF reports.

The detailed reports are uploaded as a GitHub Actions artifact and can be downloaded from the Summary page of the workflow run.

ZAP findings are also uploaded to GitHub Code Scanning and can be viewed under:

`Security -> Code scanning`

The original ZAP SARIF report is retained as part of the workflow artifact. A separate GitHub-compatible SARIF file is generated for Code Scanning by normalising the API URL locations contained in the ZAP report.

When testing from a feature branch, Code Scanning results can be viewed by filtering on the branch, for example:

`is:open branch:FLEX-328-OWASPZapimprovements`

Development scans currently use the Code Scanning category `zap-api-development`. This will be changed to `zap-api-staging` when the workflow is returned to staging.

## How to test the workflow

To test the workflow in a branch other than `main`, a few adjustments are required. This is due to the trust policy, which dictates that the staging account role can only be assumed from the `main` branch.

The workflow steps:
- Checkout your new branch
- Edit `.github/workflows/zap.yml`
    - In the Configure AWS credentials step change `secrets.STAGING_DEPLOYMENT_ROLE` to `secrets.DEV_DEPLOYMENT_ROLE`
    - In the ZAP Scan step change `secrets.STAGING_API_URL` to `secrets.DEVELOPMENT_API_URL`

Local github cli setup:
- Install `gh` cli
- Authenticate with `gh auth login`

Testing:
- Push the changes to the new branch (including the `workflow steps` modifications)
- Run `gh workflow run zap.yml --ref feature/branch`

This triggers a new run on GitHub using the branch's logic against the development environment. **Note:** Revert the workflow changes to their original values before merging into `main`.

After the workflow has completed:

- ZAP findings can be reviewed under `Security -> Code scanning`.
- Detailed ZAP reports can be downloaded from the workflow run's Artifacts section.
- The artifact is currently named `zap-api-development-reports`.

The artifact contains the HTML, JSON, Markdown, original ZAP SARIF and GitHub-compatible SARIF reports.

When testing from a feature branch, the Code Scanning page defaults to the repository's default branch. To view the results from the test branch, filter the Code Scanning results using:

`is:open branch:<branch-name>`

## How to test the OpenAPI document

The OpenAPI document used by ZAP is now generated during the workflow rather than being maintained as a static merged document.

The workflow generates the current OpenAPI specifications and creates:

`dist/openapi/merged-openapi.json`

This merged document contains the public API operations to be scanned by ZAP.

To test the OpenAPI you will need to install the [OWASP ZAP tool](https://www.zaproxy.org/download/).

Open the tool, in the toolbar go to `import` -> `Import OpenAPI Definition`. `Choose File` -> the generated OpenAPI document to verify, change the target to `localhost` and press `import`.

The results will appear as soon as it tries to import the file.

## How to deal with vulnerabilities

Vulnerability remediation must follow the [GDS Once process](https://gdsgovukagents.atlassian.net/wiki/spaces/GOS/pages/51806439/Vulnerability+Management+Process). If this process is unavailable or can't be followed, raise a ticket to initiate triage and remediation in the project JIRA space.
